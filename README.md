# 공연 좌석 예약 시스템

티켓 오픈 직후처럼 같은 공연에 요청이 몰려도 좌석이 두 번 팔리지 않도록 하는 좌석 선점·결제 이벤트 처리 서버입니다.

- Java 21, Spring Boot 4.0, Spring Data JPA
- MySQL 8.4 (InnoDB), Flyway
- 테스트: JUnit 5, Testcontainers(MySQL)
- 부하 시험: k6

설계 결정은 [DECISIONS.md](DECISIONS.md), 하지 않은 것과 감수한 타협은 [NOT-DONE.md](NOT-DONE.md), AI 도구 사용 내역은 [AI-USAGE.md](AI-USAGE.md)에 있습니다.

## 구현 범위

| 지켜야 할 조건 | 상태 | 검증 |
|---|---|---|
| 1. 같은 좌석 이중 판매 금지 | 구현 | `SeatHoldConcurrencyTest` |
| 2. 여러 좌석 선점은 전부 성공 또는 전부 실패 | 구현 | `SeatHoldConcurrencyTest` |
| 3. 같은 요청·결제 이벤트는 한 번만 반영 | 구현 | `SeatHoldConcurrencyTest`, `PaymentEventServiceTest` |
| 4. 선점 만료와 결제 승인이 동시에 일어날 때 DECISIONS.md 10번 규칙대로 처리 | 구현 | `PaymentEventServiceTest` |
| 5. 재시작 후에도 판매 확정 상태 유지 | 구현 | `RestartPersistenceTest` |
| 부하 시험 | 수행 | 아래 [부하 시험](#부하-시험) |

## 실행 방법

필요한 것: JDK 21, Docker

Gradle이 JDK를 자동으로 내려받도록 설정하지 않았으므로, JDK 21이 미리 설치되어 있어야 합니다.

```bash
./gradlew bootJar
docker compose up --build
```

- 애플리케이션: http://localhost:8080
- MySQL: `localhost:3306` (DB `seat_reservation`, 계정 `app` / `app`)

서버 두 대가 같은 DB를 쓰는 구성으로 띄우려면 `multi` 프로필을 켭니다. 두 번째 서버는 8081 포트입니다.

```bash
docker compose --profile multi up --build
```

선점 유지 시간은 `HOLD_TTL` 환경 변수(ISO-8601 기간)로 바꿀 수 있습니다. 기본값은 5분입니다.

```bash
HOLD_TTL=PT30S docker compose up --build
```

DB까지 처음 상태로 되돌리려면 `docker compose down -v`로 볼륨을 함께 지웁니다.

PC에 MySQL이 이미 설치되어 3306 포트를 쓰고 있으면 `db` 컨테이너가 뜨지 않습니다. 로컬 MySQL을 멈추거나 `docker-compose.yml`의 `db` 포트 설정을 바꿔야 합니다.

### 초기 데이터

Flyway 마이그레이션 [`V2__insert_sample_performance.sql`](src/main/resources/db/migration/V2__insert_sample_performance.sql)이 앱이 처음 뜰 때 샘플 데이터를 넣습니다.

- 공연 1개 (id `1`)
- 좌석 1,000석: A\~T열, 열마다 50석. 좌석 id는 A-1부터 순서대로 1\~1000

좌석을 만드는 API는 두지 않았습니다. 다른 공연이 필요하면 `performance`, `seat` 테이블에 직접 INSERT합니다.

## 테스트

```bash
./gradlew test
```

Docker가 실행 중이어야 합니다. 테스트가 Testcontainers로 MySQL 8.4 컨테이너를 띄워서 실제 MySQL 위에서 돕니다.
동시성 규칙이 InnoDB의 행 잠금 동작에 기대고 있어서 H2 같은 인메모리 DB로는 검증하지 않았습니다.

| 테스트 | 검증 내용 |
|---|---|
| `SeatHoldConcurrencyTest` | 같은 좌석에 50개 요청이 동시에 와도 1개만 성공 / 여러 좌석 중 하나라도 이미 잡혀 있으면 나머지도 잡히지 않음 / 사전 조회를 통과한 뒤 UPDATE에서 좌석 하나를 놓치면 이미 바꾼 좌석까지 롤백 / 겹치는 다중 좌석 요청 40개를 동시에 보내도 성공한 선점은 좌석을 전부, 실패한 선점은 하나도 갖지 않음 / 같은 Idempotency-Key 동시 요청은 선점 1개 / 같은 키로 다른 좌석을 요청하면 동시에 와도 선점 1개, 나머지는 거절 / 대소문자만 다른 사용자는 같은 키로도 각자 선점 / 선점 유지 시간에 마이크로초보다 작은 단위가 있어도 응답과 DB의 만료 시각이 같음 / 만료 작업이 동시에 여러 번 돌아도 1번만 처리 / 만료된 좌석은 만료 작업 전에도 다시 선점 가능 / 만료 처리와 만료된 좌석을 가져가는 새 선점이 동시에 돌아도 데드락 없이 새 선점이 좌석을 모두 가짐 |
| `PaymentEventServiceTest` | 승인 시 판매 확정 / 같은 이벤트 10번 동시 재전송 시 1번만 반영 / 취소가 승인보다 먼저 와도, 둘이 동시에 와도 결제의 최종 상태는 취소 / 한 선점에 서로 다른 결제의 승인이 동시에 오면 하나만 판매 / 판매 후 취소되면 좌석 재판매 가능 / 만료 전 승인은 만료 처리와 동시에 와도 판매 확정 / 만료 후 승인과 정확히 만료 시각의 승인은 환불 대상 / 만료 처리, 새 선점, 이전 선점의 늦은 승인이 동시에 와도 좌석은 한쪽에만 / 같은 좌석을 거쳐 간 만료된 두 선점의 늦은 승인이 동시에 와도 한 결제에만 판매 / 선점 취소와 승인이 동시에 와도 둘 중 하나로만 끝남 / 그사이 다른 사람이 좌석을 잡았거나, 취소된 선점이나 이미 확정된 선점에 온 승인은 환불 대상 / 대소문자나 끝 공백만 다른 `eventId`, `paymentId`는 다른 이벤트와 다른 결제 |
| `RestartPersistenceTest` | 판매 확정 후 애플리케이션 컨텍스트를 종료하고 새로 띄워도 좌석이 SOLD |
| `ApiTest` | HTTP 요청·응답 형식과 상태 코드 / 64자를 넘는 사용자 식별자나 키는 400 / 알 수 없는 선점이나 다른 선점에 연결된 결제로 온 이벤트는 422로 거절하고 재전송되어도 한 번만 보관 / 같은 결제가 서로 다른 선점으로 동시에 승인되면 한쪽만 판매하고 다른 쪽은 422로 보관 |

시간이 걸리는 만료 테스트는 실제로 기다리지 않고, 테스트용 `Clock`의 시각을 앞으로 옮겨서 확인합니다.
동시성 테스트는 작업들을 같은 순간에 출발시킨 뒤, 어느 쪽이 먼저 처리되든 최종 상태가 규칙에 맞는지 봅니다. 처리 순서에 따라 결과가 갈리는 테스트 3개(선점 취소와 승인, 만료된 두 선점의 늦은 승인, 만료·새 선점·늦은 승인)는 순서를 강제하지 않아서, 한쪽 순서만 나와도 통과합니다. 개발 중에 순서별 횟수를 임시로 출력해 세어 봤을 때는 셋 다 10회 안에 두 순서가 모두 나왔습니다. 세 번째 테스트는 그냥 동시에 시작하면 늘 같은 순서로만 처리되어, 짝수 회차에 새 선점을 50ms 늦게 시작하게 했습니다.

## API

사용자 식별 헤더(`X-User-Id`), 선점 요청의 `Idempotency-Key` 헤더, 응답 형식은 직접 정했습니다.
식별자(`X-User-Id`, `Idempotency-Key`, `holdId`, `eventId`, `paymentId`)는 대소문자와 끝 공백까지 구분합니다.

### 좌석 조회 `GET /performances/{performanceId}/seats`

```json
{
  "performanceId": 1,
  "seats": [
    { "seatId": 1, "seatNo": "A-1", "status": "AVAILABLE" },
    { "seatId": 2, "seatNo": "A-2", "status": "HELD" },
    { "seatId": 3, "seatNo": "A-3", "status": "SOLD" }
  ]
}
```

만료 시각이 지난 선점 좌석은 만료 작업이 아직 정리하지 않았더라도 `AVAILABLE`로 보여 줍니다. 실제로 그 좌석은 바로 다시 선점할 수 있습니다.

### 좌석 선점 `POST /holds`

| 헤더 | 필수 | 설명 |
|---|---|---|
| `X-User-Id` | O | 사용자 식별자, 최대 64자. 인증은 범위 밖이라 그대로 신뢰합니다. |
| `Idempotency-Key` | X | 공백 없는 1\~64자. 같은 사용자가 같은 키로 다시 보내면 선점을 새로 만들지 않고 처음 만든 선점을 돌려줍니다. |

```json
{ "performanceId": 1, "seatIds": [1, 2] }
```

| 응답 | 경우 |
|---|---|
| `201 Created` | 선점 성공 |
| `200 OK` | 같은 `Idempotency-Key`로 이미 만들어진 선점을 돌려줌 |
| `409 SEAT_UNAVAILABLE` | 요청 좌석 중 하나라도 이미 선점·판매됨. 어느 좌석도 선점되지 않음 |
| `422 IDEMPOTENCY_KEY_REUSED` | 같은 키로 다른 좌석을 요청함 |
| `400` | 헤더 누락이나 64자 초과, 빈 좌석 목록, 중복 좌석, 한 번에 10석 초과 |

```json
{
  "holdId": "0b6a6c1e-3f0e-4d4e-9b8f-6c5d6f0e2a11",
  "performanceId": 1,
  "seatIds": [1, 2],
  "status": "ACTIVE",
  "expiresAt": "2026-10-18T03:05:00Z"
}
```

`holdId`는 결제를 시작할 때 결제 제공자에게 주문 번호로 넘기는 값입니다. 결제 이벤트가 이 값으로 선점을 찾습니다.

### 선점 취소 `DELETE /holds/{holdId}`

헤더 `X-User-Id`가 필요합니다.

| 응답 | 경우 |
|---|---|
| `204 No Content` | 취소됨. 이미 취소한 선점을 다시 취소해도 204 |
| `404 HOLD_NOT_FOUND` | 선점이 없거나 다른 사용자의 선점 |
| `409 HOLD_EXPIRED` | 이미 만료됨 |
| `409 HOLD_CONFIRMED` | 결제가 끝나 판매 확정됨 |

### 결제 이벤트 수신 `POST /payment-events`

```json
{
  "eventId": "evt-123",
  "paymentId": "pay-789",
  "holdId": "0b6a6c1e-3f0e-4d4e-9b8f-6c5d6f0e2a11",
  "status": "approved",
  "occurredAt": "2026-10-18T03:01:00Z"
}
```

`status`는 `approved`, `cancelled`입니다. 응답은 `200 OK`와 처리 결과입니다.

```json
{ "eventId": "evt-123", "result": "SOLD" }
```

| result | 의미 |
|---|---|
| `SOLD` | 승인 반영, 좌석 판매 확정 |
| `REFUND_REQUIRED` | 승인됐지만 좌석을 줄 수 없어 환불 대상으로 기록 |
| `SALE_CANCELLED` | 판매 확정된 결제가 취소되어 좌석을 다시 판매 가능으로 되돌림 |
| `PAYMENT_CANCELLED` | 좌석에는 영향 없이 결제만 취소로 기록 |
| `IGNORED` | 이미 최종 상태라 반영할 것이 없음 |
| `DUPLICATE` | 이미 처리한 `eventId` |

중복이거나 무시한 이벤트도 200으로 답합니다. 실패 응답을 받은 제공자는 같은 이벤트를 계속 다시 보내기 때문입니다.
선점을 찾을 수 없거나 이미 다른 선점에 연결된 `paymentId`면 `422`로 거절하고, 운영자가 확인할 수 있게 `unmatched_payment_event` 테이블에 남깁니다. 처리 중 오류가 나면 `5xx`가 나가고, 제공자의 재전송으로 다시 처리됩니다.
상태 전이 규칙은 [DECISIONS.md](DECISIONS.md#결제-이벤트)에 정리했습니다.

## 부하 시험

### 시험한 사례

모두 제 PC에서 최종 코드로 돌렸습니다. 애플리케이션, MySQL, k6(`grafana/k6:2.3.0`)를 같은 PC의 Docker에서 실행했습니다.

- PC: AMD Ryzen 7 5700X3D (8코어 16스레드), 메모리 32GB, Windows 11, Docker Desktop (VM에 16 vCPU)
- 공통 데이터: 공연 1개, 좌석 1,000석(샘플 데이터). 요청마다 좌석 1\~4개를 연속으로 고르고, 요청의 60%는 앞 두 열(A, B열, 100석)을 노립니다.

| 사례 | 구성 | 요청 | 보려고 한 것 |
|---|---|---|---|
| 1. 기본 조건 | 서버 1대, CPU 제한 없음 | 동시 200, 총 5,000건 | 이중 판매 금지 같은 조건이 부하 중에도 지켜지는가, 무엇이 먼저 막히는가 |
| 2. 서버 2대 | 1번과 같고 서버만 2대 | 동시 200, 총 5,000건 | 서버를 늘리면 처리량이 오르는가 |
| 3. 배포 환경 흉내 | 서버마다 3코어, MySQL 4코어, k6 3코어, DB 왕복 지연 1ms. 서버 1대와 3대 | 동시 200, 총 5,000건 | 서버마다 CPU가 정해져 있고 DB가 네트워크 너머에 있을 때 |
| 4. 한계 시험 | 3번의 서버 3대 구성. 기본 설정과 연결 한계를 올린 설정 | 동시 사용자 목표 200\~80,000, 단계마다 30초 | 어디서, 무엇이 먼저 무너지는가 |

- 1, 2번 스크립트는 [`load-test/hold-load.js`](load-test/hold-load.js)이고, 동시 200, 총 5,000건으로 돌렸습니다.
- 3번의 DB 왕복 지연은 DB 컨테이너에서 나가는 패킷에 `tc netem`으로 1ms를 더한 것입니다. 서버에서 DB로 ping이 0.06ms에서 1.1ms가 됐고, k6와 서버 사이에는 지연을 넣지 않았습니다. 서버마다 커넥션 풀은 20입니다.
- 4번은 같은 스크립트를 "정해진 수의 사용자가 30초 동안 계속 요청"하도록 바꿔 돌렸습니다. k6는 서버와 같은 Docker 네트워크에서 바로 요청했습니다. Windows Docker Desktop의 포트 포워딩(`host.docker.internal`)을 거치면 4,000명에서 요청의 62%가 연결 거부로 실패해서, 서버가 아니라 포워딩이 먼저 막히기 때문입니다.
- 4번의 "연결 한계를 올린 설정"은 Tomcat의 연결 대기열(`accept-count` 100 → 10,000), 최대 연결 수(8,192 → 40,000), 작업 스레드(200 → 400)와 커널의 연결 대기열(`somaxconn`)을 늘린 것입니다.
- 3, 4번에만 쓴 설정(CPU 제한, 세 번째 서버, 지연을 거는 보조 컨테이너, 올린 연결 한계, 30초 스크립트)은 측정할 때만 임시 파일로 붙였고 저장소에는 넣지 않았습니다. 실행별 원시 기록도 저장소에는 없어서, 3, 4번 수치는 이 문서의 표로만 남아 있습니다.
- 실행 사이마다 30초씩 쉬었습니다.

### 실행 방법 (1, 2번)

```bash
./gradlew bootJar
docker compose up -d --build

# 선점·결제 기록을 지우고 좌석을 모두 빈 좌석으로 되돌린다
docker compose exec -T db mysql -uroot -proot seat_reservation < load-test/reset.sql

docker run --rm --network host -v "$PWD/load-test:/scripts" grafana/k6:2.3.0 run /scripts/hold-load.js

# 정합성 확인. 앞의 세 값이 모두 0이어야 한다
docker compose exec -T db mysql -uroot -proot seat_reservation < load-test/verify.sql
```

Windows나 macOS의 Docker Desktop에서는 `--network host`가 호스트에 연결되지 않으므로, 대신 `-e BASE_URLS=http://host.docker.internal:8080`을 넘깁니다.

서버 두 대로 돌리려면 `docker compose --profile multi up -d --build` 후 k6에 `-e BASE_URLS=http://localhost:8080,http://localhost:8081`을 넘깁니다. 요청을 두 서버에 번갈아 보냅니다.

### 측정 방법

- 처리량과 응답 시간: k6의 `http_reqs`, `http_req_duration`
- DB: 측정 전에 `performance_schema.events_statements_summary_by_digest`를 비우고, 끝난 뒤 쿼리 종류별 실행 횟수와 누적 시간을 봤습니다. 행 잠금은 `Innodb_row_lock%` 상태값의 시작과 끝 차이로 셌습니다.
- CPU: 컨테이너별 cgroup CPU 사용 시간을 실행 시간으로 나눈 평균과 `docker stats`의 1초 샘플

측정의 한계

- k6, 애플리케이션, MySQL이 같은 PC에서 돌기 때문에 실제 서버 환경의 수치로 볼 수 없습니다. 특히 커밋할 때의 디스크 동기화 시간은 이 PC 디스크의 값입니다.
- 1\~3번은 한 번 실행이 1\~2초라 CPU 평균은 대략적인 값입니다. 같은 조건에서도 실행마다 처리량이 30% 넘게 차이 났고, 예열 뒤 첫 측정이 늘 가장 느렸습니다. 처리량보다 DB 문장 수와 시간을 더 믿을 만한 값으로 봤습니다.
- k6 스크립트는 선점 요청만 보냅니다. 이 시험이 직접 확인한 것은 선점의 정합성(한 좌석에 유효한 선점이 둘 이상 걸리지 않는가, 부분 선점이 없는가)입니다. 결제 이벤트, 선점 취소, 만료 처리가 선점과 함께 몰리는 상황은 부하로 재지 않았고, 이 경로들의 동시성은 자동화된 테스트로만 확인했습니다.
- 좌석 1,000석이 금방 차기 때문에 요청의 90% 이상(4번은 99% 이상)이 409로 끝납니다. 이 시험은 "충돌이 많은 상황에서 빨리 거절하는가"를 주로 잽니다.
- k6는 응답을 받아야 다음 요청을 보냅니다(closed model). 서버가 느려지면 보내는 속도도 같이 줄어서, 실제 트래픽이 몰릴 때보다 지연이 낮게 잡힐 수 있습니다.
- 커넥션 풀 대기 시간(Hikari pending)은 직접 재지 않았습니다. 아래 풀 관련 내용은 DB 쪽 수치로 추정한 것입니다.

### 정리

선점 요청만 보낸 네 사례 모두 이중 선점, 부분 선점, 데드락은 한 번도 없었습니다. 지금 구조에서 DB 시간을 가장 많이 쓰는 곳은 성공한 선점의 커밋이고, 실패하는 요청은 잠금 없는 조회 한 번으로 끝납니다. 서버마다 CPU가 정해진 환경에서는 DB보다 서버 CPU가 먼저 찼고, 서버를 늘리면 같은 인기 좌석을 두고 커밋까지 가는 요청이 겹쳐 DB 안의 대기가 길어집니다. 사용자를 더 늘리면 처리량은 그대로이고 응답만 느려지며, 기본 설정에서는 서버가 새 연결을 받는 단계에서 먼저 실패합니다. 더 올리려면 커밋 비용 자체를 줄이거나(디스크 동기화 정책, 더 빠른 디스크), 인기 좌석으로 가는 요청을 서버 앞에서 줄이는 방법(대기열 등)을 봐야 하는데, 이번에는 하지 않았습니다.

### 개발 중에 고친 것: 실패하는 요청의 비용

부하 시험에서 요청의 90% 이상이 좌석 충돌로 실패하기 때문에, 실패하는 요청이 DB에 남기는 비용을 두 번에 걸쳐 줄였습니다.

**선점 행 INSERT 순서.** 처음 구현은 선점 행(`seat_hold`, `seat_hold_item`)을 먼저 INSERT하고 좌석을 UPDATE했습니다. 같은 `Idempotency-Key` 요청이 겹칠 때 좌석을 건드리기 전에 유니크 제약으로 걸러 내려는 의도였습니다. 그런데 실패할 때마다 선점 행을 INSERT했다가 롤백하는 비용이 DB 시간의 큰 부분을 차지했습니다. 좌석 UPDATE를 먼저 하고 성공했을 때만 INSERT하도록 순서를 바꿨습니다(DECISIONS.md 6번).

**쓰기 트랜잭션 전 사전 조회.** 순서를 바꾼 뒤에도 실패하는 요청은 모두 트랜잭션을 열고 UPDATE한 뒤 롤백했습니다. 그래서 트랜잭션을 열기 전에 잠금 없는 `SELECT COUNT(*)`로 요청 좌석이 모두 비어 있는지 먼저 보고, 하나라도 잡혀 있으면 바로 409를 돌려주도록 바꿨습니다(DECISIONS.md 6번). 최종 판단은 여전히 조건부 UPDATE가 합니다. 같은 조건으로 다시 잰 결과입니다.

| 사례 1 (3회 평균) | 바꾸기 전 | 바꾼 뒤 |
|---|---|---|
| 처리량 | 2,695\~2,858 req/s | 3,350\~4,477 req/s |
| p95 | 148\~158ms | 108\~146ms |
| `ROLLBACK` | 약 4,560회, 9.7초 | 약 57회, 0.3초 |
| 좌석 `UPDATE` | 약 5,000회, 3.5초 | 약 500회, 1.1초 |
| `SET autocommit` | 약 10,000회, 2.1초 | 약 1,000회, 0.2초 |
| 사전 조회 `SELECT` | 없음 | 약 5,000회, 3.5초 |
| 행 잠금 대기 | 210\~260회, 1\~1.4초 | 32\~47회, 0.6초 |
| 실행당 DB 문장 시간 합 | 약 26초 | 약 15초 |

- 사례 3의 "서버 1대, 지연 1ms"는 1,555 req/s에서 2,301 req/s로 올랐습니다. 거절되는 요청의 DB 왕복이 네 번(`SET autocommit`, `UPDATE`, `ROLLBACK`, `SET autocommit`)에서 한 번으로 준 것이 주된 이유로 보이지만, 요청별 시간을 따로 재지는 않아서 추정입니다.
- 사례 4에서 MySQL CPU는 4코어 한도(약 405%)를 다 쓰던 것이 230\~330%로 내려갔고, 기본 설정 200\~4,000명의 처리량이 7\~12% 올랐습니다. 32,000명의 실패율은 53%에서 21%로 줄었습니다.
- 대신 성공하는 요청은 조회가 한 번 늘었고, 좌석이 비어 있을 때 몰리는 요청은 모두 사전 조회를 통과하므로 UPDATE에서의 경쟁은 그대로입니다. 서버 3대 구성(사례 3)은 처리량이 거의 같았고, 남은 UPDATE와 COMMIT은 오히려 느려졌습니다. 연결 한계를 올린 한계 시험의 8,000\~32,000명 구간은 바꾸기 전보다 15\~27% 낮게 나왔는데, 서버 CPU가 한도에 붙어 있었고 30초짜리 1회 측정이라 원인을 가리지 못했습니다.
