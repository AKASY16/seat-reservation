# 공연 좌석 예약 시스템

티켓 오픈 직후처럼 같은 공연에 요청이 몰려도 좌석이 두 번 팔리지 않도록 하는 좌석 선점·결제 이벤트 처리 서버입니다.

- Java 21, Spring Boot 4.0, Spring Data JPA
- MySQL 8.4 (InnoDB), Flyway
- 테스트: JUnit 5, Testcontainers(MySQL)
- 부하 시험: k6

좌석 선점의 최종 판정은 MySQL의 조건부 UPDATE가 합니다. 요청한 좌석 수만큼 바뀌지 않으면 트랜잭션 전체를 롤백하고, 그 앞의 사전 조회는 이미 점유된 좌석이 섞인 요청을 빨리 거절하는 데만 씁니다.

같은 선점에 대한 결제 승인·취소와 만료 처리는 선점 행 잠금으로 하나씩 처리합니다. 결제 이벤트는 좌석·선점·결제·이벤트 기록을 한 트랜잭션에 반영해서, 같은 이벤트가 재전송되거나 처리 도중 중단돼도 한 번만 반영됩니다.

설계 결정은 [DECISIONS.md](DECISIONS.md), 하지 않은 것과 감수한 타협은 [NOT-DONE.md](NOT-DONE.md), AI 도구 사용 내역은 [AI-USAGE.md](AI-USAGE.md)에 있습니다.

## 구현 범위

| 지켜야 할 조건 | 대표 검증 |
|---|---|
| 1. 같은 좌석의 중복 선점·판매 방지 | `onlyOneHoldSucceedsForSameSeat`, `lateApprovalsOfTwoExpiredHoldsForSameSeat` |
| 2. 여러 좌석은 전부 성공하거나 전부 실패 | `partialUpdateIsRolledBack` |
| 3. 같은 요청·결제 이벤트는 한 번만 반영 | `sameIdempotencyKeyCreatesOneHold`, `concurrentDuplicateEventsAreAppliedOnce` |
| 4. 선점 만료와 결제 승인이 겹칠 때 DECISIONS.md 10번 규칙대로 처리 | `approvalBeforeExpiryWinsOverConcurrentExpiry`, `expiryTakeoverAndLateApprovalAtOnce` |
| 5. 재시작 후에도 판매 확정 상태 유지 | `soldSeatsSurviveRestart` |
| 부하 시험 | 아래 [부하 시험](#부하-시험)의 최종 버전 확인 실행 |

전체 테스트 목록은 [테스트](#테스트)에 있습니다.

## 실행 방법

필요한 것: JDK 21, Docker

Gradle이 JDK를 자동으로 내려받도록 설정하지 않았으므로, JDK 21이 미리 설치되어 있어야 합니다. 아래 명령은 Bash 기준입니다(Windows에서는 Git Bash).

```bash
./gradlew bootJar
docker compose up --build
```

- 애플리케이션: http://localhost:8080
- MySQL: `localhost:3306` (DB `seat_reservation`, 계정 `app` / `app`)

서버 두 대가 같은 DB를 쓰는 구성으로 띄우려면 `multi` 프로필을 켭니다. 두 번째 서버는 8081 포트입니다.

```bash
docker compose --profile multi up --build
```

선점 유지 시간은 `HOLD_TTL` 환경 변수(ISO-8601 기간)로 바꿀 수 있습니다. 기본값은 5분입니다.

```bash
HOLD_TTL=PT30S docker compose up --build
```

DB까지 처음 상태로 되돌리려면 `docker compose down -v`로 볼륨을 함께 지웁니다.

PC에 MySQL이 이미 설치되어 3306 포트를 쓰고 있으면 `db` 컨테이너가 뜨지 않습니다. 로컬 MySQL을 멈추거나 `docker-compose.yml`의 `db` 포트 설정을 바꿔야 합니다.

### 초기 데이터

Flyway 마이그레이션 [`V2__insert_sample_performance.sql`](src/main/resources/db/migration/V2__insert_sample_performance.sql)이 앱이 처음 뜰 때 샘플 데이터를 넣습니다.

- 공연 1개 (id `1`)
- 좌석 1,000석: A\~T열, 열마다 50석. 좌석 id는 A-1부터 순서대로 1\~1000

좌석을 만드는 API는 두지 않았습니다. 다른 공연이 필요하면 `performance`, `seat` 테이블에 직접 INSERT합니다.

## 테스트

```bash
./gradlew test
```

Docker가 실행 중이어야 합니다. 테스트가 Testcontainers로 MySQL 8.4 컨테이너를 띄워서 실제 MySQL 위에서 돕니다.
동시성 규칙이 InnoDB의 행 잠금 동작에 기대고 있어서 H2 같은 인메모리 DB로는 검증하지 않았습니다.

선점 테스트는 같은 좌석 경쟁, 부분 UPDATE의 전체 롤백, 멱등 키 충돌, 만료·재선점 경합을 검증합니다. 결제 테스트는 중복·순서 역전·지연 이벤트와 만료 경계를 검증합니다. API와 재시작 테스트는 HTTP 계약과 커밋된 판매 상태의 유지를 확인합니다.

| 테스트 | 핵심 검증 |
|---|---|
| `SeatHoldConcurrencyTest` | 같은 좌석 동시 요청은 하나만 성공, 여러 좌석은 전부 또는 전무, 같은 `Idempotency-Key`는 선점 하나, 만료와 재선점이 겹쳐도 데드락 없음 |
| `PaymentEventServiceTest` | 같은 이벤트는 한 번만 반영, 취소가 먼저 와도 결제는 취소로 끝남, 만료 전 승인은 판매·만료 후 승인은 환불 대상, 같은 좌석의 늦은 승인은 한 결제에만 판매 |
| `ApiTest` | HTTP 요청·응답 형식과 상태 코드, 잘못된 입력의 400 거절, 처리할 수 없는 결제 이벤트의 422 거절과 기록 |
| `RestartPersistenceTest` | 판매 확정 후 애플리케이션 컨텍스트를 다시 띄워도 좌석이 SOLD |

만료 시각은 테스트용 `Clock`으로 제어합니다. 경합 테스트는 관측된 결과가 규칙에 맞는지 검사하며, 모든 처리 순서의 실행을 강제하지는 않습니다.

## API

사용자 식별 헤더(`X-User-Id`), 선점 요청의 `Idempotency-Key` 헤더, 응답 형식은 직접 정했습니다.
식별자(`X-User-Id`, `Idempotency-Key`, `holdId`, `eventId`, `paymentId`)는 대소문자와 끝 공백까지 구분합니다.

### 좌석 조회 `GET /performances/{performanceId}/seats`

```json
{
  "performanceId": 1,
  "seats": [
    { "seatId": 1, "seatNo": "A-1", "status": "AVAILABLE" },
    { "seatId": 2, "seatNo": "A-2", "status": "HELD" },
    { "seatId": 3, "seatNo": "A-3", "status": "SOLD" }
  ]
}
```

만료 시각이 지난 선점 좌석은 만료 작업이 아직 정리하지 않았더라도 `AVAILABLE`로 보여 줍니다. 실제로 그 좌석은 바로 다시 선점할 수 있습니다.

### 좌석 선점 `POST /holds`

| 헤더 | 필수 | 설명 |
|---|---|---|
| `X-User-Id` | O | 사용자 식별자, 최대 64자. 인증은 범위 밖이라 그대로 신뢰합니다. |
| `Idempotency-Key` | X | 공백 없는 1\~64자. 같은 사용자가 같은 키로 다시 보내면 선점을 새로 만들지 않고 처음 만든 선점을 돌려줍니다. |

```json
{ "performanceId": 1, "seatIds": [1, 2] }
```

| 응답 | 경우 |
|---|---|
| `201 Created` | 선점 성공 |
| `200 OK` | 같은 `Idempotency-Key`로 이미 만들어진 선점을 돌려줌 |
| `409 SEAT_UNAVAILABLE` | 요청한 좌석 전체를 확보할 수 없음. 이미 점유된 좌석, 없는 좌석, 다른 공연의 좌석이 하나라도 섞이면 요청 전체가 실패하고 어느 좌석도 선점되지 않음 |
| `422 IDEMPOTENCY_KEY_REUSED` | 같은 사용자가 같은 키로 다른 공연이나 다른 좌석 묶음을 요청함 |
| `400` | 헤더 누락이나 64자 초과, 빈 좌석 목록, 중복 좌석, 한 번에 10석 초과, 정수가 아닌 공연·좌석 id(예: `990.9`) |

```json
{
  "holdId": "0b6a6c1e-3f0e-4d4e-9b8f-6c5d6f0e2a11",
  "performanceId": 1,
  "seatIds": [1, 2],
  "status": "ACTIVE",
  "expiresAt": "2026-10-18T03:05:00Z"
}
```

`holdId`는 결제를 시작할 때 결제 제공자에게 주문 번호로 넘기는 값입니다. 결제 이벤트가 이 값으로 선점을 찾습니다.

### 선점 취소 `DELETE /holds/{holdId}`

헤더 `X-User-Id`가 필요합니다.

| 응답 | 경우 |
|---|---|
| `204 No Content` | 취소됨. 이미 취소한 선점을 다시 취소해도 204 |
| `404 HOLD_NOT_FOUND` | 선점이 없거나 다른 사용자의 선점 |
| `409 HOLD_EXPIRED` | 이미 만료됨 |
| `409 HOLD_CONFIRMED` | 결제가 끝나 판매 확정됨 |

### 결제 이벤트 수신 `POST /payment-events`

```json
{
  "eventId": "evt-123",
  "paymentId": "pay-789",
  "holdId": "0b6a6c1e-3f0e-4d4e-9b8f-6c5d6f0e2a11",
  "status": "approved",
  "occurredAt": "2026-10-18T03:01:00Z"
}
```

모든 필드가 필수이고, 빠지거나 형식이 틀리면 400입니다.

| 필드 | 설명 |
|---|---|
| `eventId` | 결제 제공자가 붙인 이벤트 식별자, 최대 64자. 같은 값이 다시 오면 중복으로 처리합니다. |
| `paymentId` | 결제 식별자, 최대 64자 |
| `holdId` | 선점 응답의 `holdId`, 최대 36자 |
| `status` | `approved` 또는 `cancelled` |
| `occurredAt` | 결제 제공자에서 승인·취소가 일어난 시각(ISO-8601, 예: `2026-10-18T03:01:00Z`). 이벤트가 도착한 시각이 아닙니다. DB에 저장할 수 있는 `1000-01-01T00:00:00Z`\~`9999-12-31T23:59:59.999999Z` 범위를 벗어나면 400입니다. |

응답은 `200 OK`와 처리 결과입니다.

```json
{ "eventId": "evt-123", "result": "SOLD" }
```

| result | 의미 |
|---|---|
| `SOLD` | 승인 반영, 좌석 판매 확정 |
| `REFUND_REQUIRED` | 승인됐지만 좌석을 줄 수 없어 환불 대상으로 기록 |
| `SALE_CANCELLED` | 판매 확정된 결제가 취소되어 좌석을 다시 판매 가능으로 되돌림 |
| `PAYMENT_CANCELLED` | 좌석에는 영향 없이 결제만 취소로 기록 |
| `IGNORED` | 이미 최종 상태라 반영할 것이 없음 |
| `DUPLICATE` | 이미 처리한 `eventId` |

중복이거나 무시한 이벤트에도 200을 돌려줘 불필요한 재전송을 막습니다. 처리 중 오류는 `5xx`로 응답하고, 재전송되면 다시 처리합니다.
선점을 찾을 수 없거나 이미 다른 선점에 연결된 `paymentId`면 `422`로 거절하고, 운영자가 확인할 수 있게 `unmatched_payment_event` 테이블에 남깁니다.
상태 전이 규칙은 [DECISIONS.md](DECISIONS.md#결제-이벤트)에 정리했습니다.

## 프로젝트 구조

```
src/main/java/com/seatreservation
├── seat          좌석 조회, 좌석 상태 변경 쿼리
├── hold          선점 생성·취소·만료, 만료 스케줄러
├── payment       결제 이벤트 처리
├── performance   공연
├── config        Clock 설정
└── common        예외 처리, 시각 범위 검증
src/main/resources/db/migration   스키마와 샘플 데이터
load-test                          k6 스크립트, 초기화·검증 SQL, 개발 중 측정 기록
load-test/final-check              최종 버전 확인 실행 스크립트
```

### 측정 한계

- 서버, MySQL, k6가 같은 PC에서 돌았으므로 운영 환경의 처리 용량으로 볼 수 없습니다. 커밋할 때의 디스크 동기화 시간도 이 PC 디스크의 값입니다.
- 한 실행이 0.7\~1.5초로 짧아 처리량이 실행마다 크게 흔들렸습니다(같은 구성 안에서도 1.5\~1.6배 차이). 컨테이너 CPU 사용량은 원본 자료에 남겼지만, 짧은 실행의 평균이고 앞뒤 값을 읽는 시점이 시험 시간보다 넓어 대략적인 값입니다.
- 응답 대부분이 409라서, 이 시험은 주로 충돌이 많은 상황에서 요청을 거절하는 경로를 잽니다. 성공하는 선점이 많은 상황의 처리량은 이 결과로 알 수 없습니다.
- k6 스크립트는 선점 요청만 보냅니다. 결제 이벤트, 선점 취소, 만료 처리가 선점과 함께 몰리는 상황은 부하로 재지 않았고, 이 경로들의 동시성은 통합 테스트로만 확인했습니다([NOT-DONE.md](NOT-DONE.md)).
- 커넥션 풀에서 연결을 기다린 시간(Hikari 대기)은 재지 않았습니다(미측정). 측정 중 서버 로그에 풀 시간 초과나 ERROR·WARN이 없었다는 것만 확인했습니다.
- DB 문장 통계(`performance_schema`)는 정식 측정 직전에 비웠지만, 만료 작업의 조회와 측정 스크립트의 관측 쿼리도 함께 들어갑니다. 쿼리 형태별 표(`statements-by-digest.tsv`)는 사전 조회 수가 계정별 표보다 0\~4건 적게 잡혀서, 실행 수는 계정별 표(`statements-by-kind.tsv`)를 기준으로 봤습니다. 이 차이의 원인은 확인하지 못했습니다.
- 개발 중 시험의 1\~3번 사례는 `host.docker.internal`(Docker Desktop의 포트 포워딩)을 거쳐 요청했고, 이번 실행은 같은 Docker 네트워크에서 바로 요청했습니다. 요청 경로와 코드 버전이 달라 개발 중 수치와 직접 비교하지 않습니다.

### DB 문장 수로 본 처리 경로

계정별 문장 통계에서 센 실행 수입니다. 요청마다 사전 조회 `SELECT`가 한 번씩 돌았습니다(실행마다 5,000\~5,002건, 만료 작업의 조회 0\~2건 포함).

| 구성 | 실행 | 201 | 좌석 `UPDATE` | `COMMIT` | `ROLLBACK` | `INSERT` | 선점 수 + 선점된 좌석 수 | 사전 조회에서 끝난 409 |
|---|---|---|---|---|---|---|---|---|
| A | 1 | 467 | 529 | 467 | 62 | 1,330 | 467 + 863 | 4,471 |
| A | 2 | 430 | 491 | 430 | 61 | 1,278 | 430 + 848 | 4,509 |
| A | 3 | 429 | 504 | 429 | 75 | 1,292 | 429 + 863 | 4,496 |
| B | 1 | 426 | 503 | 426 | 77 | 1,280 | 426 + 854 | 4,497 |
| B | 2 | 450 | 537 | 450 | 87 | 1,298 | 450 + 848 | 4,463 |
| B | 3 | 448 | 528 | 448 | 80 | 1,306 | 448 + 858 | 4,472 |

- 사전 조회를 통과해 쓰기 트랜잭션을 연 요청은 좌석 `UPDATE` 수만큼이고, 그중 `COMMIT`은 201 수와 같습니다. 나머지(`ROLLBACK`)는 사전 조회와 UPDATE 사이에 다른 요청이 좌석을 먼저 선점해서, UPDATE에서 바뀐 행 수가 모자라 롤백된 요청입니다.
- `INSERT` 수는 성공한 선점의 `seat_hold`와 `seat_hold_item` 행 수의 합과 같습니다. 롤백된 요청은 선점 행을 INSERT하지 않았습니다([DECISIONS.md](DECISIONS.md) 6번).
- 409 중 "사전 조회에서 끝난 409"(409 − `ROLLBACK`)는 쓰기 트랜잭션을 열지 않고 거절됐습니다.

### 관측한 것

- DB 문장의 누적 시간은 성공한 선점의 `COMMIT`이 가장 컸습니다. 한 번 평균이 구성 A에서 15.9\~18.9ms, 구성 B에서 19.1\~25.3ms였습니다. MySQL 기본 내구성 설정(`innodb_flush_log_at_trx_commit=1`, `sync_binlog=1`)을 썼고, 디스크 동기화를 기다린 시간은 따로 나눠 재지 않았습니다.
- 구성 B의 처리량(3,350\~5,493 req/s)은 구성 A(4,663\~7,217 req/s)보다 낮게 나왔고, 두 범위는 일부 겹칩니다. B에서는 총 커넥션 풀이 40개로 늘었고, 행 잠금 대기(A 35\~52회, B 61\~72회)와 좌석 `UPDATE`의 평균 시간(A 1.2\~2.1ms, B 2.2\~3.4ms), `COMMIT`의 평균 시간이 함께 늘었습니다. 서버 두 대, MySQL, k6가 같은 PC의 CPU를 나눠 쓰는 환경이라, 이 결과만으로 서버를 늘리면 느려진다고 판단하지는 않았습니다.
- 두 구성 모두 첫 번째 정식 측정이 가장 느렸습니다. 원인은 따로 확인하지 않았습니다.
