# 개발 중 부하 시험 (탐색 자료)

개발 중에 구조를 바꿀지 판단하려고 돌린 부하 시험 기록입니다. 최종 코드로 기본 부하 조건을 다시 확인한 결과는 [README.md의 부하 시험](../README.md#부하-시험)에 있고, 이 문서의 수치는 그 결과를 대신하지 않습니다.

- 측정 시점의 코드: 사전 조회를 넣은 직후, 커밋하기 전의 작업 트리입니다(이후 커밋 `763262b`). 마지막 수정(`e546546`: 식별자 비교, 시각 정밀도, 헤더 검증, 같은 결제의 동시 연결)은 들어 있지 않습니다. "바꾸기 전" 수치는 사전 조회를 넣기 전 코드입니다.
- 원본 기록: 실행별 원시 기록과 3, 4번에 쓴 임시 설정 파일은 저장소에 넣지 않았습니다. 수치는 이 문서의 표로만 남아 있어 실행별 원본 자료와 대조할 수 없습니다.
- 환경: 애플리케이션, MySQL, k6(`grafana/k6:2.3.0`)를 같은 PC의 Docker에서 실행했습니다. AMD Ryzen 7 5700X3D (8코어 16스레드), 메모리 32GB, Windows 11, Docker Desktop (VM에 16 vCPU).
- 요청 경로: 1\~3번은 k6가 `host.docker.internal`(Docker Desktop의 포트 포워딩)을 거쳐 서버에 요청했고, 4번은 서버와 같은 Docker 네트워크에서 바로 요청했습니다. 최종 버전 확인 실행은 4번과 같은 경로라서 1\~3번 수치와 직접 비교하지 않습니다.

## 공통 조건

- 공연 1개, 좌석 1,000석(샘플 데이터)
- 요청마다 좌석 1\~4개를 연속으로 고르고, 요청의 60%는 앞 두 열(A, B열, 100석)을 노립니다.
- 1\~3번은 [`hold-load.js`](hold-load.js)로 200 VU가 총 5,000건을 보냅니다. k6는 응답을 받아야 다음 요청을 보내므로(closed model), 서버에서 늘 정확히 200건이 동시에 처리된다는 뜻은 아닙니다.
- 서버마다 커넥션 풀은 20입니다.
- 실행 사이마다 30초씩 쉬었습니다.

| 사례 | 구성 | 요청 | 보려고 한 것 |
|---|---|---|---|
| 1. 기본 조건 | 서버 1대, CPU 제한 없음 | 200 VU, 총 5,000건 | 이중 판매 금지 같은 조건이 부하 중에도 지켜지는가, DB가 어디에 시간을 쓰는가 |
| 2. 서버 2대 | 1번과 같고 서버만 2대 | 200 VU, 총 5,000건 | 서버를 늘리면 처리량이 오르는가 |
| 3. 배포 환경 흉내 | 서버마다 3코어, MySQL 4코어, k6 3코어, DB 왕복 지연 1ms. 서버 1대와 3대 | 200 VU, 총 5,000건 | 서버마다 CPU가 정해져 있고 DB가 네트워크 너머에 있을 때 |
| 4. 한계 시험 | 3번의 서버 3대 구성. 기본 설정과 연결 한계를 올린 설정 | 동시 사용자 목표 200\~80,000, 단계마다 30초 | 어디서, 무엇이 먼저 무너지는가 |

## 1. 기본 조건: 200 VU · 5,000건에서 선점 정합성 검증

예열 실행을 세 번 한 뒤 3회 측정했습니다.

| | 처리량 | 평균 | 중앙값 | p95 | 최대 | 201 | 409 | 그 밖 |
|---|---|---|---|---|---|---|---|---|
| 1회 | 3,350 req/s | 56.7ms | 43.3ms | 145.6ms | 376.7ms | 432 | 4,568 | 0 |
| 2회 | 4,477 req/s | 41.8ms | 33.0ms | 110.4ms | 319.6ms | 445 | 4,555 | 0 |
| 3회 | 4,321 req/s | 43.9ms | 36.8ms | 107.8ms | 316.4ms | 448 | 4,552 | 0 |

세 번 모두 [`verify.sql`](verify.sql)의 세 검사가 0이었고, 응답은 201 또는 409뿐이었으며, InnoDB 데드락(`INNODB_METRICS`의 `lock_deadlocks`)은 0건이었습니다. k6의 `http_req_failed`가 91%로 나오는 건 409를 실패로 세기 때문입니다.

DB 안에서 시간을 가장 많이 쓴 곳은 성공한 선점의 `COMMIT`이었습니다(3회 평균).

| 문장 | 실행 수 | 누적 시간 | 평균 |
|---|---|---|---|
| `COMMIT` | 약 440 | 약 9.9초 | 약 22.5ms |
| 사전 조회 `SELECT COUNT(*)` | 약 5,000 | 약 3.5초 | 약 0.7ms |
| 좌석 선점 `UPDATE` | 약 500 | 약 1.1초 | 약 2.2ms |
| 선점 행 `INSERT` 2종 | 약 1,290 | 약 0.4초 | 약 0.3ms |
| `ROLLBACK` | 약 57 | 약 0.3초 | 약 4.8ms |
| `SET autocommit` | 약 1,000 | 약 0.2초 | 약 0.2ms |

- 요청 5,000건 중 약 4,500건은 사전 조회에서 이미 선점된 좌석을 보고 트랜잭션을 열지 않은 채 409로 끝났습니다. 쓰기 트랜잭션을 연 요청은 약 500건이고, 그중 사전 조회와 UPDATE 사이에 좌석을 빼앗겨 롤백된 요청이 약 57건입니다.
- `COMMIT` 한 번이 평균 22.5ms로 가장 무겁습니다. MySQL 기본 내구성 설정(`innodb_flush_log_at_trx_commit=1`, `sync_binlog=1`)을 썼고, 그중 디스크 동기화를 기다린 시간은 따로 나눠 재지 않았습니다.
- DB 문장 시간의 합(실행당 약 15초)을 실행 시간(1.1\~1.5초)으로 나누면 DB 안에서 평균 10\~14개 연결이 일하고 있었다는 뜻입니다. 커넥션 풀이 20개이므로 요청 상당수가 풀에서 연결을 기다렸을 것으로 봤지만, SQL 누적 시간만으로는 풀에서 기다린 요청 수나 대기 시간을 알 수 없어 추정입니다.
- 행 잠금 대기는 실행마다 32\~47회, 총 0.6초 정도였습니다.
- CPU는 1\~2초짜리 실행의 평균이라 대략적인 값인데, 애플리케이션이 약 4.7\~8.5코어, MySQL이 약 1.6\~2코어, k6가 약 1.8\~2.3코어를 썼습니다.

## 2. 서버 2대

서버를 2대로 늘려 같은 DB를 쓰게 하면 처리량은 3,028, 4,111 req/s(2회)였습니다. 서버 1대의 범위와 겹쳤고 뚜렷한 향상은 확인하지 못했습니다. 2회 모두 `verify.sql`의 세 검사는 0이었습니다.

| | 서버 1대 | 서버 2대 |
|---|---|---|
| 처리량 | 3,350\~4,477 req/s | 3,028\~4,111 req/s |
| `COMMIT` 평균 | 약 22.5ms | 31\~32ms |
| 좌석 `UPDATE` 평균 | 약 2.2ms | 4.0\~4.4ms |
| 행 잠금 대기 | 32\~47회, 0.6초 | 63\~66회, 1.4초 |

총 커넥션 풀이 20개에서 40개로 늘면서, `COMMIT`과 `UPDATE` 시간, 행 잠금 대기가 함께 늘었습니다.

## 3. 배포 환경 흉내

- CPU 제한은 컨테이너마다 Docker의 CPU 한도로 걸었습니다(서버 3코어, MySQL 4코어, k6 3코어).
- DB 왕복 지연은 DB 컨테이너에서 나가는 패킷에 `tc netem`으로 1ms를 더한 것입니다. 서버에서 DB로 ping이 0.06ms에서 1.1ms가 됐고, k6와 서버 사이에는 지연을 넣지 않았습니다.
- 세 번째 서버, CPU 제한, 지연을 거는 보조 컨테이너는 측정할 때만 임시 파일로 붙였습니다.

| | 처리량 (평균) | p95 (평균) | 좌석 `UPDATE` 평균 | `COMMIT` 평균 | 행 잠금 대기 (실행당) |
|---|---|---|---|---|---|
| 서버 1대, 지연 없음 (1회) | 2,199 req/s | 193ms | 1.35ms | 23ms | 23회, 0.5초 |
| 서버 3대, 지연 없음 (3회) | 2,644 req/s | 171ms | 10\~16ms | 67\~89ms | 101\~126회, 4.7\~6.2초 |
| 서버 1대, 지연 1ms (3회) | 2,301 req/s | 193ms | 1.7ms | 18\~20ms | 약 41회, 0.7초 |
| 서버 3대, 지연 1ms (3회) | 2,450 req/s | 186ms | 9.8\~12.3ms | 47\~78ms | 98\~125회, 4.4\~6.1초 |

표의 10회 모두 응답은 201 또는 409뿐이었고, `verify.sql`의 세 검사는 0, 데드락도 0건이었습니다.

- CPU를 3코어로 묶으면 서버 1대는 CPU 한도(300%)까지 찼고, MySQL은 1코어 정도만 썼습니다. 1번보다 처리량이 낮게 나왔는데, CPU 한도 도달과 처리량 감소가 함께 관측된 것이고 다른 원인을 따로 나눠 보지는 않았습니다.
- 서버를 3배로 늘려도 처리량은 1.1\~1.2배였습니다. 같은 시기에 좌석 `UPDATE`가 1\~2ms에서 10ms 이상으로, `COMMIT`이 20ms 안팎에서 50\~90ms로 느려졌습니다. 같은 인기 좌석을 두고 쓰기 경쟁이 늘어난 영향으로 해석했지만 세부 원인을 분리하지는 못했습니다.
- DB 왕복 지연 1ms를 넣어도 서버 1대의 처리량은 떨어지지 않았습니다. 거절되는 요청이 DB와 한 번(사전 조회)만 왕복하기 때문으로 보지만, 실행마다 편차가 크고 3회만 재서 이것만으로 원인을 확정하지는 못했습니다.

## 4. 한계 시험

- 같은 스크립트를 "정해진 수의 사용자가 30초 동안 계속 요청"하도록 바꿔 돌렸습니다.
- k6는 서버와 같은 Docker 네트워크에서 바로 요청했습니다. 이 PC의 Docker Desktop 환경에서 포트 포워딩(`host.docker.internal`)을 거치면 4,000명에서 요청의 62%가 연결 거부로 실패하는 것을 관측해서, 포워딩을 거치지 않게 했습니다.
- "연결 한계를 올린 설정"은 Tomcat의 연결 대기열(`accept-count` 100 → 10,000), 최대 연결 수(8,192 → 40,000), 작업 스레드(200 → 400)와 커널의 연결 대기열(`somaxconn`)을 늘린 것입니다. 이 설정과 30초 스크립트도 측정할 때만 임시 파일로 썼습니다.

| 동시 사용자 (목표) | 기본 설정: 처리량 / p95 / 실패율 | 연결 한계를 올린 설정: 처리량 / p95 / 실패율 |
|---|---|---|
| 200 | 8,136 req/s / 45ms / 0% | |
| 1,000 | 7,729 req/s / 194ms / 0% | |
| 4,000 | 7,228 req/s / 777ms / 0% | |
| 8,000 | 6,247 req/s / 1.79s / 0% | 5,802 req/s / 1.92s / 0% |
| 16,000 | 2,644 req/s / 1.32s / 8.5% | 4,362 req/s / 3.84s / 0% |
| 32,000 | 2,471 req/s / 1.66s / 21% | 2,470 req/s / 8.92s / 0% |
| 48,000 (실제 약 37,000) | | 2,097 req/s / 4.71s / 0% |
| 64,000 (실제 약 42,000) | | 2,078 req/s / 5.75s / 0% |
| 80,000 (실제 약 34,000) | | 881 req/s / 9.83s / 0% |

- 두 시험의 모든 단계에서 `verify.sql`의 세 검사는 0, 데드락은 0건이었습니다. 서버의 5xx, 커넥션 풀 시간 초과, 에러 로그도 한 번도 없었습니다.
- 처리량은 동시 200명에서 약 8,100 req/s로 가장 높았고, 사용자를 늘려도 오르지 않았습니다. 이때 MySQL은 4코어 중 2.3\~3.3코어를 썼고, 서버마다 3코어 한도와 k6의 3코어 한도가 먼저 찼습니다.
- 사용자를 늘리면 처리량이 오히려 줄었고, 기본 설정에서는 연결 실패가, 연결 한계를 올린 설정에서는 긴 대기가 관측됐습니다. 기본 설정은 16,000명부터 k6에 연결 시간 초과(`dial: i/o timeout`)가 났고, 서버는 이 요청들을 받지도 못해서 트랜잭션이 시작되지 않았습니다.
- 48,000명부터는 목표 수일 뿐, k6가 사용자를 다 띄우지 못했습니다. 80,000명에서는 k6가 메모리 11.7GB를 쓰고도 34,000명만 띄웠고, Docker VM 메모리(15.9GB)가 가득 차 스왑을 쓰기 시작해서 더 올리지 않았습니다. 높은 구간에는 부하를 주는 쪽의 한계가 겹쳐 있습니다.
- 실제로 이런 트래픽을 받는다면 서버에서 줄을 세우기보다 앞단에서 들어오는 요청 수를 제한하는 쪽을 검토해야 한다고 봤습니다([NOT-DONE.md](../NOT-DONE.md)).

## 정리

기본 조건(1번)과 추가 실험(2\~4번) 모두, 시험이 끝난 뒤 `verify.sql`에서 이중 선점과 부분 선점이 나오지 않았고 데드락도 0건이었습니다. 추가 실험에서 관측한 것은 구성마다 달랐습니다. 성공한 선점의 커밋이 DB 시간을 가장 많이 썼고, CPU를 제한하면 서버 CPU가 먼저 한도에 닿았으며, 서버를 늘리면 커밋과 좌석 UPDATE가 느려졌고, 사용자를 크게 늘리면 연결 단계의 실패나 긴 대기가 나타났습니다. 이 관측을 하나의 확정된 병목으로 묶지는 않았고, 부하 발생기와 서버를 같은 PC에서 실행했다는 한계도 있습니다.

## 개발 중에 고친 것: 실패하는 요청의 비용

부하 시험에서 요청의 90% 이상이 좌석 충돌로 실패하기 때문에, 실패하는 요청이 DB에 남기는 비용을 두 번에 걸쳐 줄였습니다.

**선점 행 INSERT 순서.** 처음 구현은 선점 행(`seat_hold`, `seat_hold_item`)을 먼저 INSERT하고 좌석을 UPDATE했습니다. 같은 `Idempotency-Key` 요청이 겹칠 때 좌석을 건드리기 전에 유니크 제약으로 걸러 내려는 의도였습니다. 그런데 실패할 때마다 선점 행을 INSERT했다가 롤백하는 비용이 DB 시간의 큰 부분을 차지했습니다. 좌석 UPDATE를 먼저 하고 성공했을 때만 INSERT하도록 순서를 바꿨습니다([DECISIONS.md](../DECISIONS.md) 6번).

**쓰기 트랜잭션 전 사전 조회.** 순서를 바꾼 뒤에도 실패하는 요청은 모두 트랜잭션을 열고 UPDATE한 뒤 롤백했습니다. 그래서 트랜잭션을 열기 전에 잠금 없는 `SELECT COUNT(*)`로 요청 좌석이 모두 비어 있는지 먼저 보고, 하나라도 선점되어 있으면 바로 409를 돌려주도록 바꿨습니다(DECISIONS.md 6번). 최종 판단은 여전히 조건부 UPDATE가 합니다. 같은 조건으로 바꾸기 전과 뒤를 각각 3회 측정했습니다. 처리량과 p95는 3회의 범위이고, DB 수치는 3회 평균입니다.

| 사례 1 | 바꾸기 전 | 바꾼 뒤 |
|---|---|---|
| 처리량 (범위) | 2,695\~2,858 req/s | 3,350\~4,477 req/s |
| p95 (범위) | 148\~158ms | 108\~146ms |
| `ROLLBACK` (평균) | 약 4,560회, 9.7초 | 약 57회, 0.3초 |
| 좌석 `UPDATE` (평균) | 약 5,000회, 3.5초 | 약 500회, 1.1초 |
| `SET autocommit` (평균) | 약 10,000회, 2.1초 | 약 1,000회, 0.2초 |
| 사전 조회 `SELECT` (평균) | 없음 | 약 5,000회, 3.5초 |
